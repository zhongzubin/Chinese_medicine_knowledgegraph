# 动态多跳开发方案与验收

> 文档状态：已实现并完成自动化和真实浏览器验收
>
> 制定日期：2026-11-12
>
> 当前分支基线：`dev`
>
> 前置原则：先补功能，不做性能优化

## 1. 目标

将当前“四条固定两跳路径”升级为 **Schema 约束的 2～3 步动态多跳**：

- 从已链接实体标签和问题中的关系词出发，在 `GraphSchema.triple_patterns` 内动态搜索连续路径。
- 路径计划和执行仍由确定性代码完成，不把动态 Cypher 生成权交给模型。
- 3 步路径返回完整、可展示、可审核的逐跳证据。
- 保持现有两跳查询、安全边界和公开响应兼容。

典型新增用例：

```text
四君子汤所含药材治疗的疾病有哪些症状？
```

目标路径：

```text
Formula -HAS_INGREDIENT-> Herb
        -TREATS_DISEASE-> Disease
        -HAS_SYMPTOM-> Symptom
```

## 2. 本次不包含

- 任意深度路径。
- 变量长度 Cypher、循环路径和动态标签。
- 由模型自由生成多跳关系组合。
- 独立 Agent 子图、多 Agent 自治和动态调度。
- 延迟优化、缓存和模型调用合并。

本次是功能扩展，不以降低 P95 为验收目标。

## 3. 当前限制

| 层 | 当前限制 |
| --- | --- |
| `MultiHopQueryPlan` | 固定 2 步 |
| `RetrievalAgent` | 只匹配四条固定路径 |
| `Neo4jRepository` | 只接受 2 步连续路径 |
| `PathEvidence` | 只有两个关系和两个中间节点字段 |
| 回答与审计 | 默认第二跳目标为最终结果 |
| 前端与 CLI | 只展示两跳路径 |

## 4. 总体设计

### 4.1 动态路径规划

`RetrievalAgent` 使用 `GraphSchema.triple_patterns` 进行有界深度优先搜索：

1. 起点必须来自已链接实体的标签。
2. 路径长度仅允许 2 或 3 步。
3. 每一步必须是 Schema 中存在的三元组模式。
4. 节点标签不得重复，关系类型不得重复。
5. 路径关系集合必须与问题中识别出的关系集合一致。
6. 关系在路径中的顺序必须与问题中关系词的出现顺序一致。
7. 问题明确提到目标类型时，路径末节点标签必须匹配该提示。

只有满足全部约束且结构唯一的路径才能形成 `controlled_multi_hop` 计划；否则继续走原有属性、关系或 Schema 约束回退，不猜测路径。

### 4.2 计划契约

保持现有 `MultiHopQueryPlan` 类型和 `plan_kind`，只调整边界：

```text
MultiHopQueryPlan
- steps: list[MultiHopStep], 2 到 3 步
- used_entities: list[UsedEntityRef]
- description: str
```

`MultiHopStep` 字段不变：

```text
MultiHopStep
- subject_label
- relationship
- object_label
```

### 4.3 通用路径证据

新增内部及公开兼容模型：

```text
PathStepEvidence
- subject
- subject_label
- relationship
- object
- object_label
```

扩展 `PathEvidence`：

```text
PathEvidence
- root
- root_label
- steps: list[PathStepEvidence], 2 到 3 步
- target
- target_label
- source
```

兼容策略：

- `steps` 是后续统一使用的路径字段。
- 现有 `first_relationship`、`intermediate`、`second_relationship` 字段保留为可选兼容字段。
- 两跳结果继续填充旧字段，现有 API、CLI 和前端调用不被破坏。
- 三步结果将旧字段置空，调用方通过 `steps` 读取完整路径。
- 因为只是新增字段和扩展可选字段，`schema_version` 保持 `1.0`。

### 4.4 安全执行

`Neo4jRepository.execute_multi_hop()` 改为根据结构化步骤构造最多三步的只读 Cypher：

- 再次验证步数、节点连续性、起点标签和每一步 Schema 模式。
- 标签和关系标识符只能来自已校验 Schema，不接受用户文本拼接。
- 实体名称只进入参数 `$entity_names`。
- 不使用变量长度路径、`CALL`、动态标签或用户自定义关系。
- 顶层 `LIMIT` 继续使用 `GRAPH_QA_MAX_RESULTS`。
- 返回逐跳节点、标签和关系数组，由工作流转换为 `PathEvidence`。

### 4.5 回答和审核

- `_multi_hop_answer()` 改为按完整路径末节点分组，不再假设固定第二跳。
- 中文关系短语继续使用确定性映射。
- 证据审核逐项检查完整节点链，且至少覆盖根节点、最终目标和每个中间节点。
- 来源仍取路径根实体的 `FROM_SOURCE`；缺失时统一披露。
- 不允许三步路径绕过现有回答支持校验。

### 4.6 前端与 CLI

- `paths` SSE 事件和非流式响应结构保持名称不变。
- CLI、Streamlit 和证据审核优先读取 `steps`。
- 旧两跳响应没有 `steps` 时继续使用兼容字段。
- 三步路径使用可折叠的逐跳节点和关系展示。

## 5. 接口与配置

新增环境变量：

```dotenv
GRAPH_QA_DYNAMIC_MULTI_HOP_ENABLED=true
```

用途：在实现和灰度验证阶段控制动态规划开关。

- 默认值：`true`。
- 设置为 `false` 时回退到现有四条固定两跳路径。
- 关闭开关不回退任何安全校验。

## 7. 实施顺序

### 阶段 A：计划与证据契约

- 扩展 `MultiHopQueryPlan` 为 2～3 步。
- 新增 `PathStepEvidence`，扩展 `PathEvidence`。
- 更新模型、契约和序列化测试。

### 阶段 B：动态规划器

- 使用 Schema 三元组模式枚举 2～3 步路径。
- 增加关系集合、关系顺序、目标标签、重复节点和歧义检查。
- 保留固定两跳开关回退。

### 阶段 C：仓储与工作流

- 根据计划生成最多三步的安全 Cypher。
- 返回完整逐跳路径。
- 更新回答生成、来源披露和路径审核。

### 阶段 D：评测与前端

- 增加动态多跳固定集。
- 更新 CLI 和 Streamlit。
- 完成真实 Neo4j、API、浏览器实测和全量回归。

## 8. 测试与验收

### 8.1 单元测试

必须覆盖：

- 规划器能找到现有四条两跳路径。
- 能找到至少一条三步正向路径。
- 起点标签错误、节点不连续和 Schema 外关系被拒绝。
- 循环路径、重复节点、重复关系和超过三步的路径不被生成。
- 关系集合或顺序不匹配时不猜测路径。
- 目标标签提示不匹配时不生成动态计划。
- 多个结构候选时返回歧义并安全回退。
- 仓储生成最多三步的只读 Cypher，用户实体只进入参数。
- `PathEvidence.steps` 完整且 2～3 步连续。
- 旧两跳兼容字段保持原值。
- CLI、SSE、API 和 Streamlit 可序列化并展示三步路径。

## 9. 风险与回滚

主要风险：

- 动态搜索产生多个结构候选，导致过度猜测。
- 三步路径证据字段扩展影响 CLI、前端和审核器。
- 图数据库中的特殊关系方向产生非直觉路径。
- 路径结果数量增加导致回答和前端过长。

控制措施：

- 最大 3 步、唯一结构、不重复标签和关系。
- 所有路径仍由结构化计划执行，不使用动态 Cypher。
- 证据审核与 `LIMIT` 不放松。
- 动态多跳开关可独立关闭。

回滚方案：

1. 设置 `GRAPH_QA_DYNAMIC_MULTI_HOP_ENABLED=false` 恢复固定两跳规划。
2. 如契约变更发生问题，回退动态多跳功能提交；不修改图数据库。

## 10. 后续阶段

动态多跳验收通过后，再评估独立 Agent 子图和动态调度。独立 Agent 不应绕过本方案建立的：

- Schema 路径白名单。
- 只读 Cypher 边界。
- 最大步数和结果限制。
- 确定性证据审核。
